1. PostgreSQL Panel Helper Password Error
====================================================================================================
[ERROR SYMPTOM]
When attempting to manage or provision database credentials for apps via PostgreSQL:
"sudo: a password is required" or panel user unable to run psql operations.

[ROOT CAUSE]
1. In sudoers rules (`/etc/sudoers.d/srv-panel`), the command aliases permitted `$PANEL_USER ALL=(root) NOPASSWD: ...`
   but did NOT permit `$PANEL_USER ALL=(postgres) NOPASSWD: $PSQL_BIN`.
2. As a result, when the backend service attempted to switch user to `postgres` via `sudo -u postgres -n psql ...`
   to create databases/roles, `sudo` prompted for a password non-interactively and failed.

[INVESTIGATION & HOW WE FIXED IT]
- Inspected `scripts/install.sh`, `scripts/update.sh`, and `backend/services/postgresql_service.py`.
- Added the exact required rule to sudoers without granting overbroad `ALL=(postgres) ALL` permissions:
  `$PANEL_USER ALL=(postgres) NOPASSWD: $PSQL_BIN, /usr/bin/psql, /bin/psql`
- Verified compatibility across Debian/Ubuntu/RHEL distributions in `backend/tests/test_sudoers_compat.py`.

2. Advanced Options & Bulk Env Accordion Failure
====================================================================================================
[ERROR SYMPTOM]
Clicking the "Advanced Options" toggle or "Bulk Edit Environment Variables" button in the App Create UI
did nothing; the panels remained hidden or failed to expand.

[ROOT CAUSE]
1. CSS Specificity Conflict: In `apps-engine-optic.css`, `.apps-engine-source-grid` had `display: grid;`.
   The HTML5 `hidden` attribute or standard `.hidden` class was overridden by CSS selector specificity.
2. Inconsistent DOM Manipulation: Some JavaScript functions toggled the `.hidden` class, while others
   toggled `element.hidden = true/false` or inline `style.display = 'none'`.

[INVESTIGATION & HOW WE FIXED IT]
- In `backend/plugins/railpack_apps/static/css/apps-engine-optic.css`:
  Added: `[hidden], .hidden { display: none !important; }`
- In `backend/plugins/railpack_apps/static/js/railpack-app-create-ui.js`:
  Implemented a unified `setHidden(element, hidden)` helper that synchronized `element.hidden`,
  `element.classList.toggle('hidden', hidden)`, and `element.style.display`.
- In `backend/plugins/railpack_apps/static/js/railpack-app-create.js`:
  Wired both `data-toggle-advanced-build` and `data-toggle-bulk-env` click handlers to `setHidden()`.

3. Build Method Inspection Overriding Railpack to Dockerfile
====================================================================================================
[ERROR SYMPTOM]
When creating an app from a repository containing both a language manifest (`package.json`, `requirements.txt`, etc.)
and an auxiliary `Dockerfile`, the UI automatically changed the Build Method to "Dockerfile" instead of keeping
"Automatic (Railpack)" selected.

[ROOT CAUSE]
1. `container_app_inspection_service.py` returned `has_dockerfile = True`, and the frontend inspection handler
   unconditionally switched the selected build mode dropdown to `dockerfile`.
2. Users wanted Railpack to remain the default smart builder while showing a badge/hint that a Dockerfile was detected.

[INVESTIGATION & HOW WE FIXED IT]
- Updated `backend/services/container_app_inspection_service.py` to return `build_mode = "railpack"` whenever a
  standard application manifest is found, only returning `build_mode = "dockerfile"` if the repository contains
  *only* a `Dockerfile` and no known language manifest.
- Updated `railpack-app-create.js` and `railpack-app-create-ui.js` so `applyInspection()` sets the select box
  to the recommended `build_mode` while showing a non-intrusive "Dockerfile detected" informational hint.

4. BuildKit Host Resolution Failure
====================================================================================================
[ERROR SYMPTOM]
During Umami build step `#23 pnpm run build` (specifically `check-db` / `prisma.$queryRaw()`):
"Can't reach database server at host.docker.internal:5432"

[ROOT CAUSE]
1. Umami executes a database connectivity test during its build script (`npm-run-all check-env build-db check-db ...`).
2. Railpack delegates build step execution into the BuildKit daemon container `srv-panel-buildkit`.
3. `srv-panel-buildkit` was started without the Docker `--add-host host.docker.internal:host-gateway` flag,
   meaning the containerized build steps could not resolve `host.docker.internal` to connect to PostgreSQL on the host.

[INVESTIGATION & HOW WE FIXED IT]
- In `backend/services/container_app_deployment_service.py`, created `_ensure_buildkit_daemon()`:
  - Inspects `srv-panel-buildkit` for `ExtraHosts` containing `host.docker.internal`.
  - If missing or container is stopped, automatically recreates `srv-panel-buildkit` with `--privileged` and
    `--add-host host.docker.internal:host-gateway`.
- In `backend/plugins/railpack_apps/scripts/install_railpack_apps.sh`:
  - Added `--add-host host.docker.internal:host-gateway` to the initial build daemon creation.

5. Railpack Non-Secret Key Rejection
====================================================================================================
[ERROR SYMPTOM]
[build] Building application image.
ERRO missing environment variable: PORT. Please set the envvar with --env PORT=...
[error] Build failed. See deployment output.

[ROOT CAUSE]
1. In `container_app_deployment_service.py`, `_inject_railpack_secrets()` was passing every environment variable
   from the application `.env` file (including `PORT`, `INTERNAL_PORT`, `HOST_PORT`, `CONTAINER_PORT`) into
   `railpack.json` under the root `"secrets": [...]` array.
2. In Railpack's architecture, anything declared under `"secrets"` is treated as a **mandatory build secret**.
   When Railpack validated the build plan, it checked for `PORT` as a secret, did not find it, and halted the build.

[INVESTIGATION & HOW WE FIXED IT]
- Filtered `_inject_railpack_secrets()` in `backend/services/container_app_deployment_service.py`:
  - Explicitly excluded runtime port and network metadata: `{"PORT", "INTERNAL_PORT", "HOST_PORT", "CONTAINER_PORT"}`.
  - Only real credentials/secrets (such as `DATABASE_URL`, `REDIS_URL`, `*_SECRET`, `*_KEY`, etc.) are declared in `"secrets"`.

6. Sudo Environment Preservation Violation
====================================================================================================
[ERROR SYMPTOM]
GET https://po.tooco.net/plugins/railpack_apps/recovery/orphans 502 (Bad Gateway)
sudo: sorry, you are not allowed to preserve the environment

[ROOT CAUSE]
1. In an attempt to preserve environment variables during builds, `prefix = ["sudo", "-E", "-n"]` was added to
   `container_app_service.py` (`_run()` and `run_binary()`).
2. Linux sudoers policy (`/etc/sudoers.d/srv-panel`) enforces `Defaults:panel env_reset` and does NOT grant
   the `SETENV:` tag to the panel user.
3. As a result, every Docker inspection and management command executed via `apps._run()` was immediately rejected
   by `sudo` with return code 1: "sudo: sorry, you are not allowed to preserve the environment".

[INVESTIGATION & HOW WE FIXED IT]
- Immediately removed `-E` from `backend/services/container_app_service.py`, restoring standard `["sudo", "-n"]`.
- The orphan recovery endpoint and all general Docker management endpoints immediately returned to working order (200 OK).

7. Mutex & Lockfile Access Denied
====================================================================================================
[ERROR SYMPTOM]
╭─────────────────╮
│ Railpack 0.23.0 │
╰─────────────────╯
  ↳ Using config file `railpack.json`
  ↳ Detected Node
  ↳ Using pnpm package manager
  ↳ Found workspace with 1 packages
  ✖ Failed to create mutex: permission denied
[error] Build failed. See deployment output.

[ROOT CAUSE]
1. Railpack (written in Rust) uses inter-process synchronization mutexes and package manager caches (`mise`).
2. In earlier runs, `railpack` was executed via `sudo` (as `root` user `uid=0`), which created lockfiles and
   directories in `/tmp` (and `/root/.cache`) owned by `root:root` with restricted permissions (`0600`).
3. When `railpack` was subsequently executed as the unprivileged `srv-panel` user without `sudo`, Railpack
   attempted to open/acquire the existing `/tmp` lockfile in read-write mode. Linux kernel rejected the request
   with `EACCES (Permission denied)`.

[INVESTIGATION & HOW WE FIXED IT]
- In `backend/services/container_app_deployment_service.py`:
  Added automatic purge in `_ensure_buildkit_daemon()`: `apps._run(["rm", "-rf", "/tmp/railpack*", "/tmp/mise*"])`.
- In `backend/services/container_app_build_process_service.py`:
  Configured isolated, per-deployment temporary and cache directories:
  - `TMPDIR` -> `/srv-panel/apps/data/build/<id>/tmp`
  - `TEMP` & `TMP` -> `/srv-panel/apps/data/build/<id>/tmp`
  - `XDG_RUNTIME_DIR` -> `/srv-panel/apps/data/build/<id>/tmp`
  - `XDG_CACHE_HOME` -> `/srv-panel/apps/data/build/<id>/cache`
  - `XDG_DATA_HOME` -> `/srv-panel/apps/data/build/<id>/cache/data`
  - `XDG_STATE_HOME` -> `/srv-panel/apps/data/build/<id>/cache/state`
  - `XDG_CONFIG_HOME` -> `/srv-panel/apps/data/build/<id>/cache/config`
  This ensures Railpack never encounters lock or mutex permission conflicts.

8. Python Module Unresolved Symbol
====================================================================================================
[ERROR SYMPTOM]
[prepare] Preparing deployment.
[build] Preparing Git source and building application image.
[error] name 'Path' is not defined

[ROOT CAUSE]
When introducing the isolated directory setup in `container_app_build_process_service.py`, `Path(...)` was called
but `from pathlib import Path` had not been imported at the top of `container_app_build_process_service.py`.

[INVESTIGATION & HOW WE FIXED IT]
- Added `from pathlib import Path` to the imports of `backend/services/container_app_build_process_service.py`.
- Ran unit tests across the service modules to guarantee all symbols and type annotations resolved cleanly.

9. Sudo Environment Stripping Secrets
====================================================================================================
[ERROR SYMPTOM]
ERRO missing environment variable: DATABASE_URL. Please set the envvar with --env DATABASE_URL=...
[error] Build failed. See deployment output.

[ROOT CAUSE]
1. `railpack.json` declares `"secrets": ["DATABASE_URL"]`.
2. When `railpack build` is executed by `sudo -n`, Linux `sudo` wipes all non-whitelisted environment variables
   before spawning the child process (due to `env_reset`).
3. Because the user's live system sudoers file did not have `DATABASE_URL` in `env_keep`, `railpack` ran with an
   empty environment and threw `ERRO missing environment variable: DATABASE_URL`.

[INVESTIGATION & HOW WE FIXED IT]
- Executed `railpack build` directly under the panel user (`prefix = []` in `container_app_build_process_service.py`):
  - The panel user belongs to the `docker` group, allowing direct communication with `srv-panel-buildkit`.
  - Without `sudo`, all process environment variables (`DATABASE_URL`, `REDIS_URL`, `BUILDKIT_HOST`, custom secrets)
    are retained in `proc_env` with 100% integrity.
  - Secrets are mounted securely into BuildKit without command-line leaking or sudoers restrictions.
- Combined with the isolated `TMPDIR` and lockfile cleanup from Issue #7, builds run smoothly without mutex conflicts.
